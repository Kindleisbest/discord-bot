# Leveling activity scope — requirements planning

Andrew wants to reward any activity that keeps members engaged, including messages, replies, and received reactions. Giving a reaction must not earn XP. Staff need channel exclusions and safeguards. Andrew chose one shared set of controls: 10 XP per eligible award and a 30-second cooldown across activities, with **no daily XP cap**. The no-cap answer on 21 September replaces the earlier 1,200 XP/day default. Each advance into level n costs 10*n² XP, with no fixed maximum level. Pure progression calculations are the first implementation step; collection and earning remain unimplemented. Confirmed choices and remaining questions are maintained in [the questionnaire](LEVELING_QUESTIONNAIRE.md).

## What Discord can report

| Participation | Available signal | Counting boundary and decision status |
|---|---|---|
| Messages and replies | New message, author, channel, and reply reference | Confirmed: all new human messages, including emoji, links, and attachments, subject to cooldown/exclusions. One award opportunity per reply; edits earn nothing. |
| Forum discussions and thread replies | Thread creation plus the opening message; later messages | Confirmed: one award opportunity for a forum opening; do not count thread creation and its opening message separately. |
| Reactions received | Reaction event identifies reactor and message; message author may be included | Award the message author, never the reactor. Source message must be at most 30 days old. Verify the author when absent from the event. Ignore self/bot reactions and prevent remove/re-add farming. |
| Group voice participation | Channel membership and connection-state changes | Confirmed: at least two eligible humans, exclude AFK/deafened time, and allow muted listeners. Use the shared earning cooldown; presence does not prove attention. |
| Poll participation | Vote-add/remove events, including answer identity | Deferred at Andrew's request; ask later. Proposed once per person/poll rule is not authorized for implementation. |
| Server-event interest | Event subscription/unsubscription | Deferred at Andrew's request; ask later. This records interest or RSVP, not actual attendance. Do not label it attendance XP. |
| Time in an event's voice channel | Voice presence during an associated event | A possible participation proxy, not proof of attending or paying attention. Avoid also awarding ordinary voice XP for the same interval. External event attendance is not verified by these signals. |

Message/reply structure and forum creation are documented in Discord's [message object](https://docs.discord.com/developers/resources/message#message-object) and [forum/media thread creation](https://docs.discord.com/developers/resources/channel#start-thread-in-forum-or-media-channel). Reaction events can omit the author ID; see [reaction additions](https://docs.discord.com/developers/events/gateway-events#message-reaction-add) and [single-message retrieval requirements](https://docs.discord.com/developers/resources/message#get-channel-message).

[Voice state](https://docs.discord.com/developers/resources/voice#voice-state-object) describes connection and mute/deafen/streaming state. Speaking information belongs to the separate [voice connection protocol](https://docs.discord.com/developers/topics/voice-connections#speaking). This plan does not propose recording audio or monitoring what members say. Discord also documents [poll vote events](https://docs.discord.com/developers/events/gateway-events#message-poll-vote-add) and [scheduled-event subscriptions](https://docs.discord.com/developers/events/gateway-events#guild-scheduled-event-user-add).

## Shared controls and implementation safeguards

- Keep one shared XP amount and cooldown in the website, with the confirmed defaults above. Set channel and role exclusions centrally. There is no daily cap or daily-reset scheduler.
- Treat related Discord events as one contribution. Replies and forum openings must not accidentally gain duplicate XP.
- Received-reaction rewards ignore self/bot reactions, count a reacting person at most once per message, and use the recipient's shared cooldown. Removing and re-adding a reaction cannot earn extra XP. Earned XP stays after message/reaction deletion; staff can correct abuse. Limit eligible source messages to 30 days old; retain deduplication through the source message's eligibility window, and reject expired messages even after pruning. Store identifiers/times only, not message bodies. Define exact boundary/restart tests when implementing the collector.
- Confirmed category/channel exclusions inherit into child threads and forum posts and need to apply consistently to message, reaction, poll, and voice signals. Excluding a channel should not require storing its message bodies.
- Text content is unnecessary merely to count message events, and Andrew chose all new human messages without a short/repeated-text filter. Leveling must not require Message Content access just for counting messages. Do not add chat archiving; it remains on the separate audit branch.
- A countable event is not proof of useful engagement. Do not describe presence, RSVPs, emoji choices, or repeated contributions as verified attention or attendance.

## Implementation prerequisites

Candidate intents for the approved earning signals include `GUILDS`, `GUILD_MESSAGES`, `GUILD_MESSAGE_REACTIONS`, and `GUILD_VOICE_STATES`. Leave `GUILD_MESSAGE_POLLS` and RSVP listeners out while those choices are deferred. Member departure/rejoin detection also needs a deliberate membership-event/privileged-intent design. Check the selected feature set against Discord's [Gateway intent requirements](https://docs.discord.com/developers/events/gateway#gateway-intents) when the gateway stage begins; no new intent is enabled by this planning document or the math stage.

Design for bounded memory/storage and rate-limited processing on the Pi 3 B+. The finished leveling feature starts enabled with the agreed defaults; staff can pause it and configure exclusions. The leaderboard is all-time only. A private opt-out deletes XP and removes bot-assigned leveling reward roles; departed-member progress expires after 30 days. Staff-set milestone rewards replace earlier bot-assigned rewards and preserve manually assigned roles. Rewards update automatically after XP reductions or milestone changes. Authorized staff adjustments require recorded reasons, and full-server resets are owner-only. Separate website grants cover viewing records, adjusting XP, and managing settings/rewards; each still requires existing OAuth plus Administrator/owner checks and server isolation. Restart/reconnect handling, bounded deduplication storage, and safe role reconciliation need dedicated implementation and tests.
